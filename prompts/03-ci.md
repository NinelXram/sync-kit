# Phase 03 — CI check

You are installing sync-kit into this repository. The engine, `sync/` and the agent rules are in place. This phase
makes `sync.mjs check` run automatically: as a pull/merge request job on GitHub or GitLab, or as a local pre-commit
hook when the project has no CI.

## Goal

Depending on `state.decisions.ci`:

- `github` — `.github/workflows/sync-check.yml` runs `check` and `contract-check` on every pull request.
- `gitlab` — `sync/ci/sync-check.gitlab-ci.yml` holds the `sync-check` merge request job and `.gitlab-ci.yml`
  includes it with one line.
- `none` — `sync/hooks/pre-commit` is committed as an executable file and activated on this machine.

## Preconditions

- You are at the repository root.
- Phases 01 and 02 are done or skipped: `node sync/scripts/sync.mjs state show` lists `"01"` and `"02"` under
  `phases`. If not, stop and tell the user which prompt to run first.
- `decisions.ci` is `github`, `gitlab` or `none`. If it is missing, ask the user and record it with
  `node sync/scripts/sync.mjs state decide --ci <github|gitlab|none>` (with `none`, also `--channel none`).

## Inputs

- `node sync/scripts/sync.mjs state show` — `decisions.ci`.
- `sync/.kit/discovery.md` — CI facts from phase 00: `workflow:` block, runner tag candidates.
- Templates in the kit: `.sync-kit/kit/ci/github/sync-check.yml`, `.sync-kit/kit/ci/gitlab/sync-check.gitlab-ci.yml`,
  `.sync-kit/kit/ci/hooks/pre-commit`.

## Steps

1. Run `node sync/scripts/sync.mjs state show` and read `decisions.ci`. Do **only** the matching step: 2 for `github`,
   3 for `gitlab`, 4 for `none`. Then continue with step 5. If the CI choice changes to `none` in this phase
   (recorded with `state decide --ci none --channel none`), also set `"channel": "none"` under `notify` in
   `sync/sync.config.json` (change nothing else there) and run `node sync/scripts/sync.mjs check`.

2. **`ci: github`**
   1. Copy the template (the command fails instead of overwriting):
      ```
      node -e "const fs=require('fs');fs.mkdirSync('.github/workflows',{recursive:true});fs.copyFileSync('.sync-kit/kit/ci/github/sync-check.yml','.github/workflows/sync-check.yml',fs.constants.COPYFILE_EXCL)"
      ```
      If it fails with `EEXIST`, `.github/workflows/sync-check.yml` already exists (e.g. a hand-made sync check from
      before the kit): show it to the user, say what the kit version runs instead (`check` and `contract-check` with
      the globs from `sync/sync.config.json`), and ask before replacing it. Only if they agree, overwrite it:
      ```
      node -e "require('fs').copyFileSync('.sync-kit/kit/ci/github/sync-check.yml','.github/workflows/sync-check.yml')"
      ```
      If they refuse, keep the file unchanged and continue with step 5 (`doctor` still requires it to run
      `sync.mjs check`).
   2. If the copied file contains `__DEFAULT_BRANCH__`, replace every occurrence with the repository's default branch
      (the output of `git symbolic-ref --short refs/remotes/origin/HEAD` without the leading `origin/`; ask the user if
      that command fails). The check workflow runs on every pull request, so usually there is nothing to replace.
   3. Change nothing else in the file.

3. **`ci: gitlab`**
   1. Copy the job file into the repository:
      ```
      node -e "const fs=require('fs');fs.mkdirSync('sync/ci',{recursive:true});fs.copyFileSync('.sync-kit/kit/ci/gitlab/sync-check.gitlab-ci.yml','sync/ci/sync-check.gitlab-ci.yml',fs.constants.COPYFILE_EXCL)"
      ```
      If `sync/ci/sync-check.gitlab-ci.yml` already exists, compare it with the template and ask the user before
      replacing it.
   2. **Runner.** Ask the user, suggesting the runner tag candidates from discovery:
      - which runner tags the job needs (none if shared/instance runners pick up untagged jobs);
      - whether that runner uses the **docker** or the **shell** executor. Shell executor: the `image:` line is
        ignored and the runner machine itself must have Node.js 18+ on its `PATH` — ask the user to confirm (e.g. by
        running `node --version` on the runner). Docker executor that cannot pull `node:22` (no access to Docker Hub):
        ask for the internal image to use and replace `node:22` in this file with it.
   3. In `sync/ci/sync-check.gitlab-ci.yml`, replace the line `  # SYNC_KIT_RUNNER_TAGS` (keep the two-space indent)
      with `  tags: ["<tag>"]` (several tags: `  tags: ["<tag1>", "<tag2>"]`), or delete the line when no tag is
      needed.
   4. **Check `.gitlab-ci.yml` for a `workflow:` block.** If it has a top-level `workflow:` with `rules:` and no rule
      mentions `merge_request_event`, stop here: explain to the user that merge request pipelines are probably
      disabled, so the `sync-check` job would never run, and that changing `workflow:` is their decision. Continue
      only after the user has changed it or tells you to continue anyway.

      If `.gitlab-ci.yml` has **no** `workflow:` block and its jobs run in branch pipelines (no job uses
      `merge_request_event` or `only: [merge_requests]`), explain this to the user before going on: the MR-only
      `sync-check` job makes GitLab create a **separate merge request pipeline** that contains only `sync-check`,
      next to the usual branch pipeline with the project's tests. With "Pipelines must succeed" enabled, the merge
      request may then follow that small pipeline instead of the project's tests. GitLab's standard fix is a
      `workflow:` block that switches between branch and merge request pipelines:
      ```yaml
      workflow:
        rules:
          - if: $CI_PIPELINE_SOURCE == "merge_request_event"
          - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
            when: never
          - if: $CI_COMMIT_BRANCH
      ```
      With it, a branch with an open merge request runs one merge request pipeline with all jobs; jobs that have
      their own `rules:` / `only:` excluding merge request pipelines must be checked. Adding it is the user's
      decision: show the block, never add or change `workflow:` without explicit consent, and continue either way
      once the user has decided. Mention it again in the final summary if they kept the current setup.
   5. **Include the job — ask the user first.** Show the exact change and wait for consent. Then edit `.gitlab-ci.yml`:
      - it has an `include:` list → append exactly one item, aligned with the existing items:
        `- local: 'sync/ci/sync-check.gitlab-ci.yml'`;
      - it has an `include:` with a single value (a string or one mapping) → ask the user, then turn it into a list
        whose first item is the existing value and whose second item is the line above;
      - it has no `include:` → add at the very top of the file:
        ```yaml
        include:
          - local: 'sync/ci/sync-check.gitlab-ci.yml'
        ```
      - there is no `.gitlab-ci.yml` → ask the user, then create it with only the block above.

      Use one `- local:` item per file, never a wildcard path (wildcard includes need GitLab 13.11; the kit supports
      GitLab 13.7+). Change nothing else in `.gitlab-ci.yml`.
   6. Tell the user to check on GitLab after merging: the next merge request must show a `sync-check` job in its
      pipeline. If it does not, the `workflow:` rules or runner tags are the usual cause.

4. **`ci: none`** (local pre-commit hook)
   1. Tell the user first: without CI there are no chat notifications, and the hook is best effort — each developer
      must activate it, it can be skipped with `git commit --no-verify`, and it does not replace a CI check.
   2. Copy the hook:
      ```
      node -e "const fs=require('fs');fs.mkdirSync('sync/hooks',{recursive:true});fs.copyFileSync('.sync-kit/kit/ci/hooks/pre-commit','sync/hooks/pre-commit',fs.constants.COPYFILE_EXCL)"
      ```
   3. Track it as executable — required, because files committed from Windows lose the exec bit. Run these two
      commands one after the other:
      ```
      git add sync/hooks/pre-commit
      git update-index --chmod=+x sync/hooks/pre-commit
      ```
      `git ls-files -s sync/hooks/pre-commit` must now start with `100755`.
   4. If `.gitattributes` has no rule for it, ask the user whether to add the line `sync/hooks/* text eol=lf` to
      `.gitattributes` (a shell script checked out with Windows line endings can fail to run). Add it only if they
      agree, and `git add .gitattributes`.
   5. Commit the hook. First list what is staged:
      ```
      git diff --cached --name-only
      ```
      If anything other than `sync/hooks/pre-commit` (and `.gitattributes`, if the user agreed to step 4) is staged,
      show the list to the user and ask whether to commit it too or to unstage it (`git restore --staged <path>`) —
      do what they decide. Then commit **without a path argument** (`git commit … -- <path>` re-reads the file from
      disk and drops the exec bit on Windows):
      ```
      git commit -m "chore(sync): add sync pre-commit hook"
      ```
      Check the committed mode: `git ls-tree HEAD sync/hooks/pre-commit` must start with `100755`. If it shows
      `100644`, run `git update-index --chmod=+x sync/hooks/pre-commit` and commit again (no path argument).
   6. **Activate it.** Look for an existing hook manager:
      - **husky** (`.husky/` directory): append the line `sh sync/hooks/pre-commit` to `.husky/pre-commit` (create the
        file if missing).
      - **lefthook** (`lefthook.yml`, `lefthook.yaml` or `.lefthook.yml`): add under `pre-commit:` → `commands:` an
        entry `sync-check:` with `run: sh sync/hooks/pre-commit`.
      - **pre-commit framework** (`.pre-commit-config.yaml`): add under `repos:` a `- repo: local` entry with the hook
        `id: sync-check`, `name: sync-check`, `entry: sh sync/hooks/pre-commit`, `language: system`,
        `pass_filenames: false`.

      With a hook manager, ask the user before editing its config, change only that entry, and do **not** change
      `core.hooksPath`.

      Without a hook manager:
      1. List the active hooks that `core.hooksPath` would hide:
         ```
         node -e "const fs=require('fs');const d=require('child_process').execSync('git rev-parse --git-common-dir').toString().trim()+'/hooks';console.log(fs.existsSync(d)?fs.readdirSync(d).filter(f=>f.endsWith('.sample')===false).join('\n'):'')"
         ```
      2. If it prints any file name, tell the user those hooks will stop running once `core.hooksPath` points to
         `sync/hooks`, and ask what to do (move them into `sync/hooks/`, keep them and skip activation, or accept
         hiding them). Follow their decision.
      3. Activate on this machine:
         ```
         git config core.hooksPath sync/hooks
         ```
      4. Add one line to the project-rules block of `sync/README.md` (between `<!-- sync-kit:project-rules:start -->`
         and `<!-- sync-kit:project-rules:end -->`, in the config language) telling every developer to run
         `git config core.hooksPath sync/hooks` once after cloning.

5. **Run the checks locally:**
   ```
   node sync/scripts/sync.mjs check
   node sync/scripts/sync.mjs contract-check --base HEAD~1
   ```
   `check` must exit `0`. `contract-check` only warns; in a repository with a single commit it prints that it skipped
   and exits `0`.

## Hard rules

- Never modify the project's existing CI workflows or jobs. The only allowed changes to existing CI files, each only
  after the user agreed: the single `include` item in `.gitlab-ci.yml` (plus turning a single-value `include:` into a
  list), the GitLab `workflow:` rules block of step 3.4 when the user explicitly asked for it, and replacing an
  existing `.github/workflows/sync-check.yml` with the kit template (step 2.1).
- Never copy engine files; `sync/scripts/` is managed only by `sync.mjs install`.
- Edit a hook manager config (husky, lefthook, pre-commit) only with the user's consent, adding only the sync entry.
- Never change `core.hooksPath` when a hook manager is in use, nor before telling the user which hooks it would hide.
- Never ask for or write secrets; this phase needs none.
- Never write `sync/.kit/state.json` by hand; only through `sync.mjs state`.
- Apart from the hook commit of step 4, do not run `git commit`; only suggest it. Never commit the hook with a path
  argument (`git commit -- <path>`).

## Outputs

- `github`: `.github/workflows/sync-check.yml`.
- `gitlab`: `sync/ci/sync-check.gitlab-ci.yml` and one `include` item in `.gitlab-ci.yml` (plus the `workflow:` block
  of step 3.4 only if the user chose it).
- `none`: committed `sync/hooks/pre-commit` (mode `100755`), hook activated through a hook manager or
  `core.hooksPath`, an activation line in the project-rules block of `sync/README.md` when `core.hooksPath` is used.

## Verify

```
node sync/scripts/sync.mjs doctor --phase 03
```

The exit code must be `0` and no line may start with `✗`. Acceptable `!` warnings: `pre-commit hook is active on this
machine` (other developers activate it themselves), `core.hooksPath=… does not hide existing hooks` when the user
accepted hiding them in step 4, and the GitLab `workflow:` warning when the user decided to keep their rules.
